### Current Reconciliation Strategy at Despegar

- Oracle handles card reconciliation with 88% success rate on new monthly coupons
  - April: 120k lines processed, 105k reconciled, 15k pending
  - March: 153k total coupons processed
  - Uses one-to-one matching: merchant + installment + amount
- Manual processes handle many-to-many cases outside Oracle
  - Extract installment numbers from both sides
  - Group by reservation number, card details, authorization codes
  - Current system limitations prevent automated many-to-many

### Reconciliation Logic Requirements

- One-to-one matching (primary strategy):
  - Merchant code + installment number + installment count + amount
  - Must match installment-by-installment, not full receipt level
  - Example: installment 8 of 10 matches only with installment 8 of 10
- Many-to-many grouping (secondary strategy):
  1. Group by reservation number (when available)
    - 40% of Cielo coupons lack reservation numbers in current SFTP data
    - Newer data should have complete reservation coverage
  2. Group by BIN + last 4 digits + authorization code (fallback)
  3. Group by authorization code only (final fallback)
- Amount comparison vs. join logic:
  - Use gross amount in comparison (not join) for grouping strategies
  - Tolerance of 1 real for amount matching
  - Receipts require formula: receipt amount + CCP to get gross amount

### Banking Validation Process

- Pre-reconciliation bank validation required before processing coupons
- Cross-check liquidations against bank statements by:
  - Bank + description matching (e.g., Cielo pays through BTG bank)
  - Date-based validation of settlement amounts
- Only upload coupons for dates that match bank settlements exactly
  - Mismatched dates remain pending until resolved
  - Both bank entries and liquidations held back for investigation
