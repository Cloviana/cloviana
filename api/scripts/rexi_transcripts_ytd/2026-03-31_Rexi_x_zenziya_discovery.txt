### Zenziya: Company & Problem

- Fintech lending to the base of the pyramid in Central America; primary market discussed: Dominican Republic
- Borrowers pay via bank transfer → reconciliation is the core pain
  - 2 banks, \~8–10 distinct payment modalities (in-branch, ATM, digital transfer)
  - \~25,000–30,000 transactions/month
  - All payments require a proof-of-payment (voucher photo or screenshot), processed via OCR
- Current match rate: \~90–95% same-day, \~99% within 2 days
- Key matching challenge: payer identity often absent or mismatched in bank extract
  - e.g., borrower pays from someone else’s account; comprobante shows a different name/ID than the extract
  - Edge case flagged: fraudulent vouchers with altered dates

### Current Setup & Pain Points

- Robot scrapes bank portals hourly (no API available) → downloads CSV → loads to GCP/BigQuery
  - Robot has failed before: banks detect it, close session, or disable the user
- Some existing AI for identity inference across transactions
- 3 people dedicated full-time to reconciliation
- Also uses an external vendor for identification
- Characterization: “eficaz más que eficiente” — functional but manual-heavy, not scalable
- No financial losses or regulatory risk currently; purely an efficiency/automation initiative
- Priority: exploratory, no urgency — evaluating build vs. buy

### Fit & Key Discussion Points

- GCP/BigQuery already in use → Rexi has existing GCP integration, speeds implementation
- Existing robot connector: preference to reuse if stable; replace if it causes downstream risk
- Matching logic is rule-based and case-specific — Rexi’s approach is to absorb that institutional knowledge during implementation and encode it into the agent
- Zenziya asked about “community” (payment type) error rate management
  - Current process: activate a payment type, monitor error rate for a month, pause and retrain if it exceeds threshold
  - Rexi’s approach: sandbox testing before go-live; no production release until match logic is validated
- Deployment model: SaaS (cloud) most likely fit
- Pricing model: flat fee based on volume, connector count, and complexity — no per-transaction scaling
- Implementation timeline: live in production in <30 days; implementation fee rebated if hit together
- Support: self-serve via Rexi Agent for config; SLA document covers uptime commitments
